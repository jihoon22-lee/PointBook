# 포인트번호 식별자 전환 및 누적 장부 이관 설계

## 목적

PointBook의 업무상 계정 식별자를 `이름 + 개인번호`에서 정규화된 8자리
`point_no`로 전환한다. 같은 스키마에서 일반 인원과 공용카드를 관리하고,
사용자가 제공한 누적 장부를 2024-05부터 2026-08까지의 월별 이력으로 안전하게
이관한다.

이 문서는 `PointBook_Codex_Work_작업명세.md`와 로컬 저장소 및 DB 조사 결과를
합친 구현 기준이다. 원본 엑셀, 실제 DB, 백업, 실데이터 보고서는 저장소에 넣지
않는다.

## 확인된 기준 상태

- 저장소 기준 브랜치: `main`의 `fc5439a`
- 현재 Alembic revision: `96588aa65d2d`
- 실제 DB: `data/pointbook.db`
- 실제 DB의 업무 데이터: 월 스냅샷 0건, 잔액 기록 0건, 테스트 인원 2명
- 사용자는 위 테스트 인원 2명의 삭제를 승인했다.
- 수정 원본은 첫 지급 열 `F`가 `5월분`인 80,221바이트 파일이다.
- 원본 재검증: 일반 인원 74명, 공용 계정 4개, 28개월, 잔액 기록 1,392건,
  active/inactive 44/30명, 음수 순사용 5건
- 2024-05: 33건, 지급 및 총잔액 1,385,000원
- 2026-08: 이월 2,848,212원, 지급 1,716,000원, 총잔액 4,564,212원

## 데이터 모델

`Person.id`와 기존 외래키는 그대로 유지한다. `people`에 다음 필드를 적용한다.

- `point_no VARCHAR(8) NOT NULL UNIQUE`: 업무상 유일 식별자
- `account_type VARCHAR(20) NOT NULL DEFAULT 'person'`: `person` 또는 `shared`
- `personal_no`: 일반 인원에게는 업무상 필수지만 DB에서는 공용 계정을 위해 NULL 허용

기존 `UNIQUE(personal_no, name)` 제약은 제거한다. `usage` DB 컬럼은 기존 코드와
마이그레이션 호환성을 위해 유지하되, 계산과 화면의 의미는 부호 있는 `순사용`으로
바꾼다.

포인트번호 정규화는 한 서비스에서만 수행한다. 공백과 하이픈을 제거한 뒤 숫자
8자리인지 검사하고 DB에는 공백 없는 값을 저장한다. 화면에서는 `0000 0001`
형태로 표시한다.

## 기존 DB 안전 전환

Alembic 마이그레이션은 기존 인원이 있어도 애플리케이션 부팅이 실패하지 않도록
각 기존 행에 `L0000001`처럼 ID를 포함한 8자리 고유 임시값을 넣은 뒤 `point_no NOT NULL UNIQUE`
제약을 완성한다. 이 임시값은 정상 업무용 값으로 인정하지 않는다.

누적 장부 importer는 다음 순서로 임시값을 제거한다.

1. 이름과 개인번호가 정확히 한 원본 계정과 일치하면 해당 `point_no`로 백필한다.
2. 일치하지 않는 기존 계정이 있으면 기본적으로 중단한다.
3. `--replace-empty-history-people`가 명시되고, 기존 월 스냅샷과 잔액 기록이 모두
   0건일 때만 일치하지 않는 기존 일반 계정을 삭제한다.
4. 실제 DB에서는 사용자가 삭제를 승인한 테스트 인원 2명에 이 옵션을 사용한다.
5. apply 완료 전에 NULL, 임시값, 형식 오류, 중복이 하나라도 있으면 rollback한다.

마이그레이션 자체에는 실명, 개인번호, 포인트번호 매핑을 넣지 않는다. 따라서 공개
git 이력에는 개인정보가 남지 않는다.

## 월간 요청서 흐름

`RequestRow`는 필수 `point_no`를 가진다. 붙여넣기와 AI 결과는 포인트번호 누락이나
형식 오류를 거부한다. `sync.analyze()`는 정규화된 `point_no`만으로 기존 계정을
찾고, 같은 번호의 이름·개인번호·팀·계급 변경은 새 계정이 아닌 프로필 변경으로
계획한다.

한 요청서 안에서 정규화 후 같은 포인트번호가 두 번 나오면 확정을 차단한다. 검수
화면의 이월잔액 키는 `개인번호|이름` 대신 `point_no`를 사용한다. `shared` 계정은
요청서에 없어도 inactive로 전환하지 않는다.

## 순사용

공식은 다음과 같다.

```text
순사용 = 가장 최근 이전 기록의 total - 이번 carry_balance
```

이전 기록이 없으면 0이다. 음수는 0으로 자르지 않는다. UI와 문서에서 `사용`은
`순사용`, `총 사용`은 `순사용 합계`로 바꾸고, 양수는 순감소·음수는 적립 또는
이전 등에 따른 순증가임을 안내한다. 통계와 차트도 signed 값을 그대로 합산한다.

## 누적 장부 파서

기존 세로형 단월 importer와 별개로 `app/services/ledger_import.py`를 만든다. 파서는
`간식비` 시트와 A:E 기본 정보를 검증하고 2:75 상세행만 읽는다. 76·77행 집계값은
읽지 않는다.

월 매핑은 코드에 28개 열 범위를 명시한다. `F`는 2024-05이고, `G:I`부터 `CG:CI`
까지는 2024-06부터 2026-08이다. 각 3열 블록의 잔액 헤더 월 + 1개월을 교차
검증하며, 지급 헤더의 알려진 오기는 경고만 남긴다.

각 사람과 월은 독립적으로 판정한다.

- 2024-05는 F가 있을 때만 `carry=0`, `amount=F`, `usage=0`, `total=F`로 생성한다.
- 이후 블록의 세 셀이 모두 비면 기록을 만들지 않는다.
- 지급액만 비면 0으로 저장한다.
- 잔액 또는 합계가 필요한데 비어 있으면 오류다.
- `total != carry + amount`이면 오류다.
- 순사용은 바로 전 달이 아닌 해당 사람의 가장 최근 이전 기록으로 계산한다.

공용카드는 CJ:CL에서 읽고 계정만 생성한다. 팀 공용은 해당 팀에 연결하고 소방서
공용은 팀을 비운다. 공용카드에는 이번 이관에서 월별 기록을 만들지 않는다.

## dry-run과 apply

CLI 기본 동작은 dry-run이다. dry-run과 apply는 같은 파서·검증·DB 계획 객체를
사용한다. 콘솔에는 마스킹된 건수, 금액, 월 범위, 경고 위치만 표시하며 실명이나
전체 식별자는 출력하지 않는다.

apply는 다음 안전장치를 가진다.

1. 원본 검증과 예상값 대조
2. DB 현재 상태와 월 충돌 검사
3. 실제 DB 백업
4. 선택적으로 이력 없는 테스트 인원 교체
5. 팀·계정·스냅샷·기록·현재 상태를 한 트랜잭션으로 저장
6. 사후 불변식 검사 후 commit, 실패 시 rollback
7. 같은 월이 있으면 재적용 차단

## UI와 통계

인원 추가·수정·목록·상세, 팀 상세, 월간 검수, 대시보드에 포인트번호와 계정
유형을 반영한다. 포인트번호 검색을 지원하고 표시할 때만 공백을 넣는다. 일반 인원은
개인번호를 계속 입력해야 하며 공용 계정은 비워둘 수 있다. 재직자 인원 통계에서는
`account_type=person`만 센다.

## 개인정보와 배포

원본 `.xlsx`, 실제 `data/*.db`, 백업, 실데이터 보고서, 스크린샷은 커밋하지 않는다.
테스트는 합성 인물과 합성 workbook만 만든다. 사용자 제공 `scripts/deploy.sh`는
비밀정보를 포함하지 않는 것을 확인한 뒤 브랜치에 포함한다.

실DB 적용 직전에는 PointBook Uvicorn(`app.main:app`, 127.0.0.1:8002)만 중지하고,
타임스탬프 백업을 만든다. 적용 후 서버를 다시 시작하고 검색·개인 이력·대시보드·
월간 검수 smoke test를 수행한다.

## 검증과 완료 경계

단위·통합 테스트, 85% 이상 coverage, Ruff, mypy, Alembic upgrade/check, Docker E2E를
통과한다. 실데이터 dry-run 값이 명세와 모두 일치할 때만 apply한다. 실제 DB 적용 후
78개 계정, 28개 월, 1,392개 기록, 44/30 상태, 음수 순사용 5건과 최초·최종 합계를
다시 SQL로 검증한다.

그 후 개인정보가 git diff/history에 없음을 검사하고 한국어 PR을 만든다. CI
`Quality gate`가 통과한 뒤 squash merge한다. Windows 7 Chrome 109, Android 실기기,
운영 접근성은 이 환경에서 직접 확인할 수 없으므로 자동/E2E 검증과 구분해 보고한다.
